# Project context — PX4 ↔ ROS 2 companion link (uXRCE-DDS over Ethernet)

This file is project context for Claude Code. It captures confirmed hardware/software facts and architectural decisions for the PX4–RPi5 communication bridge. Treat items under "Confirmed" as ground truth; treat items under "Open / not yet confirmed" as unresolved — do not assume they are done.

## Goal

Deploy a VIO (Visual-Inertial Odometry) system based on OpenVINS on a Holybro X500 v2 drone, feeding pose estimates into PX4's EKF2 via the uXRCE-DDS ROS 2 bridge, running the ROS 2 stack on a Raspberry Pi 5 companion computer connected to the Pixhawk 6X over **Ethernet**.

---

## Hardware — confirmed

| Component | Detail |
|---|---|
| Airframe | Holybro X500 v2 |
| Flight controller | Pixhawk 6X (board target `fmu-v6x`, MCU STM32H753, Cortex-M7 @ 480MHz) |
| Companion computer | Raspberry Pi 5, 16 GB RAM |
| Stereo camera (VIO input) | OAK-D Pro (Luxonis) |
| Pixhawk 6X Ethernet | Physically exposed. Connector: **JST-GH 4-pin** (not raw RJ45 — same locking connector family as TELEM/GPS ports, vibration-resistant). PHY: Microchip, integrated with STM32H753 MAC. Link speed: **100 Mbps** (Fast Ethernet, not Gigabit — MCU MAC limitation). |
| RPi5 Ethernet | Standard RJ45, Gigabit, single physical port. Will auto-negotiate down to 100 Mbps when linked to Pixhawk. |

## Network architecture — decision made

**Chosen channel: Ethernet** (not UART/TELEM2, not USB-serial). Rationale already evaluated and settled: greater bandwidth margin, better EMI immunity (differential vs single-ended UART), Ethernet allows MAVLink-to-GCS and uXRCE-DDS-to-companion to coexist on the same physical interface (different UDP ports) — unlike UART, which is mutually exclusive between the two.

- Protocol: **uXRCE-DDS over UDP**. Client runs on PX4 (compiled in firmware), agent runs on RPi5.
- Requires a physical **JST-GH 4-pin ↔ RJ45 adapter cable/board** (e.g. BotBlox-style) to connect Pixhawk's Ethernet connector to RPi5's RJ45 port. **Status: acquired.**
- IP addressing: PX4 uses the `netman` module (verified in the fork's `src/systemcmds/netman/netman.cpp` and `Kconfig`). The settings live in **non-volatile memory**, not in `net.cfg`. `net.cfg` (`/fs/microsd/net.cfg`, keys `DEVICE=`, `BOOTPROTO=` (`static`|`dhcp`|`fallback`), `IPADDR=`, `NETMASK=`, `ROUTER=`, `DNS=`) is only an import/export file: at boot `netman update -i eth0` (from `rcS`) reads it, stores it in non-volatile memory, **deletes the file and reboots**; so a missing `net.cfg` is normal and proves nothing. Commands in NSH: `netman show` (current persistent settings), `netman save` (export current settings to `/fs/microsd/net.cfg` for editing), `netman update -i eth0`. Firmware default on fmu-v6x (`CONFIG_NETINIT_DHCPC=y`): `BOOTPROTO=fallback` = try DHCP first, and if nobody answers use the static fallback `10.41.10.2` (`CONFIG_NETMAN_FALLBACK_IPADDR=0xA290A02`; default router/DNS `10.41.10.254`). Recommended plan: `BOOTPROTO=static` on both sides, PX4 = `10.41.10.2`, RPi5 = `10.41.10.1` (applied on the RPi5; PX4 side: see open items).
- PX4 parameters to set via QGroundControl (not yet set — pending hardware bring-up):
  - `UXRCE_DDS_CFG` = `Ethernet`
  - `UXRCE_DDS_PRT` = `8888` (default; same port used in the agent command below)
  - `UXRCE_DDS_AG_IP` = RPi5 IP, encoded as int32 via `PX4-Autopilot/Tools/convert_ip.py` (PX4 params don't support strings)
  - `UXRCE_DDS_DOM_ID` (default `0`, reboot required) — **must equal the `ROS_DOMAIN_ID` of the shell that consumes `/fmu/*`**, otherwise the topics are simply invisible. Trap in this repo: `entrypoint.sh` exports `ROS_DOMAIN_ID=42` (so tmux shells started by the container are on 42), `dockerRun.sh` sets `0` (so a `docker exec` shell is on 0). Decision pending: either set `UXRCE_DDS_DOM_ID=42` on PX4 or run the bridge shells with `ROS_DOMAIN_ID=0`.
  - Reboot (not reflash) required after changing these.
- Agent command on RPi5: `MicroXRCEAgent udp4 -p 8888`
- Docker networking: use `--network host` on the container running the agent/ROS 2 stack — traffic is UDP unicast point-to-point, no NAT/port-mapping needed. `dockerRun.sh` already starts the container with `--net=host`.
- **Known consequence to handle**: RPi5 has only **one** physical Ethernet port. Dedicating it to the Pixhawk link means the RPi5 loses its normal network uplink on that interface. Plan: use RPi5's onboard WiFi for SSH/dev/network access, OR a USB-Ethernet adapter if WiFi is disabled in flight (e.g. to avoid RC/telemetry interference). **Status: decision not yet made.**

## VIO → PX4 integration specifics

- Target ROS 2 topic: `/fmu/in/vehicle_visual_odometry`, message type `px4_msgs::msg::VehicleOdometry`
- **Versioned topics get a `_v<N>` suffix at runtime** (`generate_topic_name()` in the client's `utilities.hpp`, from the message's `MESSAGE_VERSION`; verified in the fork, 2026-09-21): `VehicleStatus` and `VehicleLocalPosition` are version 1 → `/fmu/out/vehicle_status_v1`, `/fmu/out/vehicle_local_position_v1`. `VehicleOdometry`, `VehicleAttitude`, `VehicleCommand`, `TrajectorySetpoint` are version 0 → no suffix, so the visual-odometry input stays `/fmu/in/vehicle_visual_odometry`. `dds_topics.yaml` does not show the suffix.
- **What OpenVINS actually outputs (verified in `ov_msckf/src/ros/ROS2Visualizer.cpp`, fork commit `0bbddfd`, 2026-09-21)**: `poseimu` (`PoseWithCovarianceStamped`, at camera-update rate), `odomimu` (`nav_msgs/Odometry`, **at IMU rate** via `fast_state_propagate`, only starting 1 s after initialisation), `pathimu`; frame_id `global`, child `imu`. Pose = pose of the **IMU** in `global`; the quaternion is already Hamilton `q_ItoG` in ROS `(x,y,z,w)` order (source comment: "a rotation GtoI in JPL has the same xyzw as an ItoG Hamilton rotation"). `global` is gravity-aligned, **z up**, origin at the IMU start position; x/y come from `InitializerHelper::gram_schmidt` (`ov_init/src/utils/helper.h`): `z = accel_mean/|accel_mean|`, then `x = z × e_k` with `e_k` the IMU axis (x or y) most perpendicular to gravity, `y = z × x`. Worked by hand for a level, forward-looking camera and `R_CI ≈ I` (true in our calibration: `T_cam_imu` of cam0 has ~identity rotation, so IMU axes = camera optical axes): `global` = **FLU with x = the drone's heading at initialisation** (not a fixed compass direction). Not yet verified empirically. `odomimu` is only computed/published **if it already has a subscriber** (`pub_odomimu->get_subscription_count() != 0` guard, `ROS2Visualizer.cpp:283`) — a bridge node that doesn't subscribe gets nothing, it isn't a silent no-op. **`twist.linear`/`twist.angular` are in the IMU's own (local/body) frame, not `global`** — confirmed by reading `Propagator::fast_state_propagate` (`ov_msckf/src/state/Propagator.cpp:251`): `state_plus.block(7,0,3,1) = quat_2_Rot(q_Gtoi) * v_iinG` explicitly rotates the internally-global-frame velocity into the IMU frame before it's returned (comment: "local frame v_iinI"); this resolves the "to be confirmed empirically" note this doc previously had — it was confirmed by code, not by flight test. Covariances come from the filter (`cov_plus`), pose 6x6 = position then orientation. Initialisation is static (`init_dyn_use: false`): the platform must be still, then move. Config in use for the OAK-D Pro: IMU `update_rate: 192`.
- **`T_i_b` (in `kalibr_imu_chain.yaml`, meant to be "IMU to body") is dead configuration**: grepped across `ov_core`, `ov_init`, `ov_msckf` — zero uses. OpenVINS has no concept of a "vehicle body frame"; everything it outputs is in the physical IMU frame and its own `global` world frame. Do not try to compensate the drone-mounting rotation by editing this field — it does nothing. That conversion is done in `px4_vio_bridge` instead (see below).
- **`colcon_ws/src/open_vins/config/px4_stereo` is a leftover Gazebo/SITL example config, not the real hardware calibration** — its `kalibr_imucam_chain.yaml` has non-identity `T_cam_imu` rotations and its `rostopic:` fields point at `/world/baylands/...` (a Gazebo world), inconsistent with "no PX4 SITL/Gazebo in the workflow" above. The real, in-use OAK-D Pro calibration is `colcon_ws/src/open_vins/config/oakdpro_calib05_newImucalib` (real topics `/oak/left/image_rect`, `/oak/right/image_rect`, `/oak/imu/data`; `T_cam_imu` rotation for cam0 ≈ identity, confirming `R_CI ≈ I` above).
- **What PX4's `VehicleOdometry` wants (verified in the fork's `msg/versioned/VehicleOdometry.msg`)**: `q` is Hamilton in **(w, x, y, z)** order (different from ROS `(x,y,z,w)`), rotation body→world; `pose_frame = POSE_FRAME_FRD` means "FRD, constant arbitrary heading offset, z down" (exactly a VIO world frame); `velocity_frame` has `FRD` and `BODY_FRD`; `*_variance` are 3-vectors (variances only); `reset_counter` must be bumped on VIO re-initialisation; unknown fields = NaN; timestamps are converted by the client when `UXRCE_DDS_SYNCT=1` (default), so use the RPi clock (ROS time) for `timestamp`/`timestamp_sample`. EKF2 vision parameters present in the fork: `EKF2_EV_CTRL` (bitmask: 0 horizontal pos, 1 vertical pos, 2 3D velocity, 3 yaw), `EKF2_EV_DELAY` (ms), `EKF2_EV_NOISE_MD`, `EKF2_EVP_NOISE`, `EKF2_EVV_NOISE`, `EKF2_EVA_NOISE`, `EKF2_EVP_GATE`, `EKF2_EVV_GATE`, `EKF2_EV_QMIN`, `EKF2_EV_POS_X/Y/Z` (position of the vision sensor in body FRD; the code uses `EKF2_EV_POS_* − EKF2_IMU_POS_*`, i.e. the offset **from the Pixhawk's IMU**, rotated with the EKF attitude, also used with the gyro for the velocity lever arm), `EKF2_HGT_REF`.
- **How EKF2 uses the vision frame (verified in the fork's `ekf2/EKF/aid_sources/external_vision/*.cpp`)**: EKF2 works in NED world / FRD body (quaternion body→NED); it only knows north if it has a heading source (mag, GNSS). `pose_frame`/`velocity_frame` are **fields of each `VehicleOdometry` message**, not PX4 parameters. With `POSE_FRAME_FRD`: (a) if EV yaw fusion is off (`EKF2_EV_CTRL` bit 3 = 0) EKF2 keeps its own yaw and filters the constant rotation between its frame and the vision frame (`_ev_q_error_filt`) to rotate EV position/velocity into NED; (b) if EV yaw fusion is on, EKF2 yaw follows the vision yaw and the world becomes the vision frame (no north needed, no magnetometer dependence indoors). With GNSS active, EV yaw is not allowed unless the EV frame is NED.
- **Frame conversion is required and not optional**: PX4/EKF2 expects **FRD** (Forward-Right-Down). OpenVINS output is typically FLU/ENU-like. A bridge node must explicitly convert position/orientation/velocity and set `pose_frame`/`velocity_frame` (e.g. `POSE_FRAME_FRD`) accordingly. This is the most common source of "position estimate drifts/resets to zero" bugs in this exact combination (OpenVINS + PX4) per community reports.
- **QoS**: PX4 publishers/subscribers use `BEST_EFFORT`. ROS 2 default is `RELIABLE`. The bridge node's publisher must use a compatible (`BEST_EFFORT`) QoS profile or messages will be silently dropped with no error.
- Minimum publish rate: 30 Hz (if covariances included) / 50 Hz — below this, EKF2 discards the vision input.
- Relevant EKF2 parameters (set via QGroundControl, reboot required):
  - `EKF2_EV_CTRL` — bitmask enabling fusion of vision position/velocity/yaw (this replaced the older `EKF2_AID_MASK`; don't follow tutorials referencing `EKF2_AID_MASK`, they're outdated)
  - `EKF2_HGT_REF` — height reference source (set to vision if flying GPS-denied/indoor)
  - `EKF2_EV_DELAY` — vision-to-IMU timestamp delay compensation, must be tuned empirically (rotate the vehicle, compare vision topic timestamps against `sensor_combined`/gyro)
- **`px4_msgs` comes from the PX4 fork, not from `PX4/px4_msgs`**: https://github.com/FedericoDD/PX4-Autopilot/tree/PX4-Autopilot/v1.17.0 (**private repo** — clone only on the host, where git has credentials; the container has none). It is a git submodule at `px4-ws/PX4-Autopilot` (branch `PX4-Autopilot/v1.17.0`, `update = none` in `.gitmodules`), deliberately **outside** `px4-ws/src`, and the workspace is built with `colcon build --base-paths src`. Being outside `src` is not enough on its own: colcon's default base path is the current directory (`.`), so without `--base-paths src` it scans all of `px4-ws` and picks up the fork's own files as packages — `PX4-Autopilot/msg/CMakeLists.txt` became a package named `msg` and failed (`px4_list_make_absolute` not found, verified 2026-09-21), and `msg/px4_msgs_old` and `msg/translation_node` show up as duplicates.
  - **Sparse checkout**: of the whole fork only `msg/`, `srv/` and `Tools/copy_to_ros_ws.sh` are needed (everything the ROS side depends on from PX4 is the message definitions; the firmware is already flashed). The submodule is therefore checked out shallow + partial (`--filter=blob:none`) + sparse: ~1.4 MB working tree and ~2.6 MB git dir instead of ~406 MB + ~255 MB (`docs/` alone is 329 MB).
  - Initialise it on the host with **`./scripts/init_px4_submodule.sh`** (needs git ≥ 2.25). The sparse patterns are local git config of each clone, not versioned, which is why a script is needed. `.gitmodules` has `update = none` so that a plain `git submodule update --init` skips this submodule instead of fetching the full tree. Re-run the script after a pull that moves the submodule pointer: it re-aligns the checkout to the pinned commit. Do not check it out with `git submodule update --checkout`, and do not use `--recursive` (the fork has ~29 nested submodules).
  - `entrypoint.sh` builds `/root/px4-ws` (mounted from `px4-ws/` by `dockerRun.sh`): it runs the fork's `Tools/copy_to_ros_ws.sh`, which copies the fork's `.msg`/`.srv` into `px4-ws/src/px4_msgs` plus `px4_msgs_old` and `translation_node`, then `colcon build`. Only the messages are built, **never the PX4 firmware**. The `px4_msgs` scaffolding (CMakeLists/package.xml) is cloned from upstream `PX4/px4_msgs` branch `release/1.17` (verified to exist), otherwise the script would clone `main`. `px4-ws/src/` is generated and git-ignored.
  - The fork adds a custom message `light_board.msg` (not in upstream). Its name is not CamelCase, which `rosidl` does not accept, so `entrypoint.sh` excludes it from `px4_msgs` (it is a MAVLink-streamed uORB topic, unrelated to the DDS bridge). Re-check this if a bridge topic ever needs it.
  - Existing containers do not have the new `px4-ws` volume mount: recreate the container with `dockerRun.sh` and rebuild the image.

## VIO → PX4 bridge node — implemented (2026-09-22), reception by PX4 verified on the bench (2026-09-24), EKF2 fusion not yet tested

`colcon_ws/src/px4_vio_bridge` is a Python `ament_python` ROS 2 package, subscribing to OpenVINS's `odomimu` (`nav_msgs/Odometry`) and publishing `px4_msgs/msg/VehicleOdometry` on `/fmu/in/vehicle_visual_odometry`. Not part of `entrypoint.sh`'s build/mount list before this change — now wired into `dockerRun.sh` (new volume mount), `entrypoint.sh` (new `colcon build --packages-select px4_vio_bridge` step, after the OpenVINS build) and the top-level `Makefile` (`make vio-bridge`). Full details, including the derivation of the frame math, are in the package's own `README.md` — this entry only records the decisions that affect the rest of the project.

- Node: `px4_vio_bridge/vio_to_px4_bridge.py` (executable `vio_to_px4_bridge`). Launch: `launch/vio_bridge.launch.py`, taking a `config_path` argument (defaults to `config/vio_bridge.yaml`).
- **Whole-pipeline launch (2026-09-24, not yet run)**: `launch/vio_pipeline.launch.py`, run with `make vio-pipeline` (passes `CAMERA_CONFIG`/`OPENVINS_CONFIG`/`VIO_BRIDGE_CONFIG`, so the Makefile stays the only place where config paths live; `camera_params_file` and `openvins_config` have no default on purpose). It starts agent → depthai → OpenVINS → bridge. Start order is **not** needed for correctness (DDS pub/sub is decoupled, every node waits for its inputs); it is enforced anyway so that a broken stage stops the launch with a clear reason instead of leaving a half-working pipeline. Each stage waits for a *readiness check*, not just a spawned process (`OnProcessStart` only means spawned). The checks run through the `wait_for_topics` helper (console script in the same package): PX4 data on `/fmu/out/vehicle_status_v1` (skip with `require_px4:=false`) → a message on each OpenVINS input topic, parsed from the OpenVINS config the same way `ROS2Visualizer` does → the bridge's `input_topic` **publisher exists**. The last check deliberately does not wait for a message: because of the `odomimu` subscriber-count guard, it would deadlock. Other decisions: `ROS_DOMAIN_ID` is forced from `ros_domain_id` (default 42) for all processes, which removes the `docker exec` = domain 0 trap; the depthai include is wrapped in a scoped `GroupAction` (Humble's `IncludeLaunchDescription` does not scope launch configurations); OpenVINS runs with `emulate_tty=True` + `output='both'`, because its `printf` output is block-buffered on a pipe; a crash of the agent/OpenVINS/bridge shuts everything down. The launch does not call `make` itself: `make → sh → ros2 run` does not forward launch's SIGINT/SIGTERM and would leave orphaned processes (e.g. holding the camera).
- **Timestamps**: uses `msg.header.stamp` from the incoming OpenVINS message for both `timestamp` and `timestamp_sample` — never `self.get_clock().now()`. This was an explicit requirement: the bridge's own scheduling jitter must not leak into `EKF2_EV_DELAY` compensation as if it were camera-pipeline latency.
- **QoS**: subscriber reliability is a parameter (`input_qos_reliability`, default `reliable`, matching OpenVINS's `create_publisher<T>(topic, 2)` default). Publisher reliability is **hardcoded `BEST_EFFORT`** in code, not exposed as a parameter — a deliberate footgun-prevention choice, since PX4's uXRCE-DDS client only accepts `BEST_EFFORT` and a misconfigured `RELIABLE` publisher here fails silently (see "QoS" bullet above).
- **Frame conversion**, implemented as two independent fixed rotations (derivation and math in the package README):
  1. World: `global` (FLU, z-up) → `POSE_FRAME_FRD` (z-down) — a constant 180° rotation about x, fixed by the message convention, **not** configurable.
  2. Body: OpenVINS IMU frame → drone body FRD — the `imu_to_body_rotation_deg: [roll, pitch, yaw]` parameter in `config/vio_bridge.yaml` (aerospace ZYX, degrees). Default `[90, 0, 90]` is exactly the OAK-D Pro optical-axis → FRD permutation (`FRD_forward=IMU_z, FRD_right=IMU_x, FRD_down=IMU_y`), derived from `R_CI ≈ I` above. **Only correct if the OAK-D Pro is mounted level and forward-facing**; any additional physical mounting misalignment on the airframe must be measured and composed into these three angles by whoever installs the sensor — this is not derivable from the repo.
  - `velocity_frame` is set to `VELOCITY_FRAME_BODY_FRD` (not `FRD`/nav-frame), because `odomimu.twist` is confirmed to be IMU-frame, not world-frame (see `Propagator.cpp:251` note above) — so only the body rotation applies to `velocity`/`angular_velocity`, not the world flip.
  - Covariance: `position_variance`/`velocity_variance` are the diagonal of the rotated 3×3 covariance block (`R · Σ · Rᵀ`), exact for the default axis-permutation rotation. `orientation_variance` is rotated the same way under the **assumption** that OpenVINS's attitude-error covariance is expressed IMU-frame — this assumption is not verified empirically, flagged in both the code and the package README.
- **Known gap — `reset_counter`**: always published as `0`. `odomimu` carries no VIO re-initialisation signal, so the bridge cannot detect a filter reset yet. EKF2 relies on this counter to know the vision origin jumped; add detection (e.g. discontinuity watch, or a future OpenVINS status topic) before relying on the bridge across a re-init.
- **First bench run with the real hardware — verified 2026-09-24 (props off, EKF2 vision fusion still off, reported by the user)**: full chain agent ↔ PX4 → OAK-D Pro driver → OpenVINS (`oakdpro_calib05_newImucalib`, static init) → `vio_to_px4_bridge` running in the container (`ROS_DOMAIN_ID=42`). Checks that passed:
  - ROS side: `ros2 topic hz /fmu/in/vehicle_visual_odometry` above the 30–50 Hz EKF2 minimum; `ros2 topic info -v` shows the bridge publisher as `BEST_EFFORT` with the agent's subscription attached; `ros2 topic echo --once` shows `pose_frame = 2` (FRD), `velocity_frame = 3` (BODY_FRD), a normalised `q`, finite variances (no NaN), `timestamp == timestamp_sample`, non-zero.
  - PX4 side (NSH / QGC MAVLink Console): `uorb top vehicle_visual_odometry` shows the uORB topic being published at the same rate as on the ROS side; `listener vehicle_visual_odometry` shows the same values as ROS and a recent `timestamp_sample`, so timesync/timestamp conversion works with the bridge using `msg.header.stamp`.
- **Not yet done**: (a) enabling EKF2 fusion (`EKF2_EV_CTRL`, `EKF2_HGT_REF`, `EKF2_EV_DELAY`) and checking `estimator_status_flags` (`cs_ev_*`) / `estimator_aid_src_ev_pos`/`_vel` (fused, `test_ratio` < 1); (b) the manual-movement frame test (forward → x+, right → y+, up → z−, clockwise yaw → heading+ in both `/fmu/in/vehicle_visual_odometry` and `/fmu/out/vehicle_local_position_v1`), i.e. the axis signs of the frame conversion are **not yet validated empirically**; (c) measuring the real `imu_to_body_rotation_deg` for however the OAK-D Pro ends up mounted on the X500 v2 frame (still the default, which assumes level/forward-facing); (d) tuning `EKF2_EV_DELAY`.

## Camera stream viewer (`oak_stream_server`) — tooling, not part of the PX4 bridge

Implemented 2026-09-22, unrelated to VIO/PX4: a debug convenience so `/oak/left/image_rect` can be eyeballed from a laptop browser without `rviz2`/X11 forwarding. `colcon_ws/src/oak_stream_server` (Python `ament_python`), a Flask app running in the same process as a ROS 2 node — `rclpy.spin()` on one thread, `Flask.run(threaded=True)` on another, sharing only a lock-protected "latest JPEG frame" buffer. Served as MJPEG (`multipart/x-mixed-replace`) on `http_host:http_port` (default `0.0.0.0:5000`).

- **Explicit design constraint from the user**: the local network (Wi-Fi) is trusted, so **no authentication/TLS** — do not expose this port beyond the LAN.
- Reachable on the RPi5's Wi-Fi IP with zero extra Docker networking config: the container already runs `--net=host` (needed for uXRCE-DDS, see above), so Flask binding inside the container binds directly to the host's interfaces, `0.0.0.0` included.
- `fps_limit`/`jpeg_quality` (in `config/oak_stream.yaml`) trade directly against RPi5 CPU, which OpenVINS also needs (no GPU on this board) — kept low (10 fps default) on purpose, this is a debug viewer, not a telemetry-grade feed.
- **Flask itself is installed via `apt` (`python3-flask`) directly in the `Dockerfile`, not declared in the package's `package.xml`**: it has no dependable `rosdep` key, and a failing/unknown key there would break `rosdep install --from-paths src` for the *entire* `colcon_ws` (OpenVINS and `px4_vio_bridge` included), not just this package. `cv_bridge`/OpenCV, which this package also needs, already come from the existing rosdep step (`ov_core`/`ov_init`/`ov_msckf` already depend on `cv_bridge`), so no Dockerfile change was needed for those.
- Wired into the same places as `px4_vio_bridge`: `dockerRun.sh` (new volume mount), `entrypoint.sh` (new `colcon build --packages-select oak_stream_server` step), `Makefile` (`make oak-stream`). A container created before this change needs recreating (`dockerRun.sh`), same caveat as for `px4_vio_bridge`/`px4-ws`.

## TagSLAM ground truth — separate ROS 2 Jazzy container (2026-10-01, implemented, not yet built or run)

Tooling for `ov_eval`, unrelated to the PX4 bridge. Goal: no more ROS 2 → ROS 1 bag conversion and no more copying bags to the ROS 1 `kalibr-TagSLAM` (Noetic) container. Layout and usage are in the README ("TagSLAM Workspace"); this entry records the decisions and what was verified.

- `tagslam-ws/` follows the `depthai-ws`/`px4-ws` pattern: submodule `tagslam-ws/src/tagslam` (`berndpfrommer/tagslam`, branch `ros2`, pinned at `714f03a`), `tagslam-ws/Dockerfile` (`FROM ros:jazzy`), `tagslam-ws/entrypoint.sh` (builds TagSLAM with colcon, `-j2`, `RelWithDebInfo`, `BUILD_TESTING=OFF`), host launcher `./dockerRun_tagslam.sh` (image `tagslam-jazzy`, container `tagslam`, `--rm`, no `--net=host`/`--privileged`). It mounts `colcon_ws/src/open_vins` at the same path as `dockerRun.sh`, so the Makefile targets `tagslam-detect` / `tagslam-run` / `tagslam-gt` use the same paths in both containers. The Humble `Dockerfile` and `entrypoint.sh` are untouched.
- **Why Jazzy and not the Humble container (verified by reading upstream at `714f03a`)**: `src/enhanced_player.cpp` subclasses `rosbag2_transport::Player` and calls `get_publishers()`, and `tagslam_from_bag` / `sync_and_detect_from_bag` configure the player through node parameters (`storage.uri`, `play.clock_publish_on_topic_publish`, `play.start_paused`, ...) and a parameterised `Recorder`. None of that exists in Humble's rosbag2 (`player.hpp` on the `humble` branch has neither the parameter-driven mode nor `get_publishers()`), and the upstream README/CI only target Jazzy/Rolling. A Humble backport would mean rewriting those executables and keeping a fork.
- All dependencies are apt packages for Jazzy on **amd64 and arm64** (checked in the ROS apt index, 2026-10-01): `ros-jazzy-gtsam` 4.2.0, `flex-sync` 2.0.1 (contains everything on `flex_sync` master, so the `tagslam.repos` source import is not needed), `apriltag-detector{,-umich,-mit,-draw}` 3.1.0, `apriltag-msgs` 2.0.2. Hence a single submodule.
- A Humble-recorded rosbag2 (sqlite3, metadata version 8, only `sensor_msgs/Image` and `Imu`) is read as it is by Jazzy: same on-disk format and message types. `extract_gt.py` uses `rosbags.AnyReader`, which already reads rosbag2 directories, so it needs no change; TagSLAM ROS 2 writes `/tagslam/odom/body_<name>` (same topic name as ROS 1) to the bag named by its `outbag` parameter.
- **Traps found in the upstream code** (both handled or documented): (1) `tagslam_from_bag` leaves its loop after the first message when `max_number_of_frames` is its default 0 (`getNumberOfFrames() >= num_frames`), so the Makefile passes 1000000; (2) `outbag` is resolved against the working directory, not `output_directory`, so the Makefile passes an absolute path.
- **Detector settings are not equivalent to ROS 1**: ROS 2 `sync_and_detect` instantiates the detector plugin with its defaults (family 36h11, black border 1, no decimation) and exposes no parameter for them; the ROS 1 `sync_and_detect.launch` used the MIT detector with `black_border_width` 2. The `cameras.yaml` keys also changed (`rostopic` → `image_topic`, raw images instead of `annotated_images`; `tagtopic` → `tag_topic`; `tag_detector: umich|mit`).
- `kalibr-TagSLAM` is not touched: it remains the ROS 1 place for Kalibr calibration. The `rosbag-postprocessing` Makefile target (`rosbags-convert`) is now needed only for Kalibr.
- Alternative not taken: moving the whole repo to Jazzy (one container). It would also align with the PX4 docs' Jazzy recommendation, but needs DepthAI (`v3_humble` fork), OpenVINS and the uXRCE-DDS agent (2.4.3) to be re-validated on the hardware.
