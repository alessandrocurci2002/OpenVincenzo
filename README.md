# ROS 2 Humble + OpenVINS + DepthAI + PX4 (uXRCE-DDS) — Docker Environment

A Docker environment for OAKDPRO with ROS 2 Humble, OpenVINS, and DepthAI support, plus the uXRCE-DDS bridge to a PX4 flight controller (Pixhawk 6X over Ethernet). PX4 SITL is **not** used: the bridge is developed and tested directly against the real hardware.

Project context, hardware facts and architectural decisions for the PX4 ↔ ROS 2 link are in [CLAUDE.md](CLAUDE.md).

## PX4 Workspace (px4_msgs)

ROS 2 needs the PX4 message definitions (`px4_msgs`) to talk to the flight controller, and they must match the firmware. They are taken from the PX4 fork the firmware is built from, not from the upstream `PX4/px4_msgs`:

- submodule: `px4-ws/PX4-Autopilot` → https://github.com/FedericoDD/PX4-Autopilot, branch `PX4-Autopilot/v1.17.0` (**private repo**: it is cloned on the host, where git has credentials, and mounted into the container)
- **sparse checkout**: of the whole fork only `msg/`, `srv/` and `Tools/copy_to_ros_ws.sh` are needed, everything else is firmware source (the firmware is already flashed). The submodule is checked out shallow + partial (`--filter=blob:none`) + sparse by `./scripts/init_px4_submodule.sh`: ~1.4 MB of working tree and ~2.6 MB of git data, instead of ~660 MB (`docs/` alone is 329 MB)
  - the sparse patterns are local git config of each clone and cannot be stored in `.gitmodules`, hence the script; `.gitmodules` sets `update = none` so that a plain `git submodule update --init` skips this submodule instead of downloading the full tree
  - the script is idempotent: re-run it after a `git pull` that moves the submodule pointer, it re-aligns the checkout to the pinned commit
  - do not check the submodule out with `git submodule update --checkout`: that would download the full tree
- it sits outside `px4-ws/src` on purpose, and the build runs `colcon build --base-paths src`: without `--base-paths`, colcon scans the whole workspace root (its default base path is `.`) and would pick up files of the fork as packages (`msg/CMakeLists.txt` as a package named `msg`, which fails, plus duplicate copies of `px4_msgs_old` and `translation_node`)
- `entrypoint.sh` runs the fork's `Tools/copy_to_ros_ws.sh`, which fills `px4-ws/src` with `px4_msgs` (the fork's `.msg`/`.srv`), `px4_msgs_old` and `translation_node`, then builds the workspace with `colcon` and sources `/root/px4-ws/install/setup.bash`
- only the messages are built, **never the PX4 firmware**
- `light_board.msg` (custom message of the fork, not CamelCase, not used by the DDS bridge) is excluded from `px4_msgs` because `rosidl` does not accept its name
- if the submodule is not initialised, `entrypoint.sh` prints a warning pointing to `./scripts/init_px4_submodule.sh` and skips this step

## uXRCE-DDS Agent

The Micro XRCE-DDS Agent is installed in the image (`/usr/local/bin/MicroXRCEAgent`). The PX4 docs pair ROS 2 Humble with Fast-DDS 2.6.x and agent 2.4.2 (the DDS version is decided by the ROS distro), so the agent is built against the Fast-DDS/Fast-CDR that ships with ROS in `/opt/ros/humble` (`UAGENT_USE_SYSTEM_FASTDDS/FASTCDR=ON`, like `micro_ros_agent` does on Humble) instead of bringing its own copy: there is a single Fast-DDS in the container. The agent therefore needs ROS 2 sourced, as it is in the container shells. PX4 runs the client (already compiled in the firmware), the agent runs here. Transport: UDP over Ethernet, the container uses `--net=host`.

```bash
MicroXRCEAgent udp4 -p 8888
```

The PX4-side setup (static IPs, `UXRCE_DDS_*` parameters) is described in [CLAUDE.md](CLAUDE.md).

## Verify the installation

`scripts/check_px4_bridge.sh` checks, **without hardware**, that everything built correctly: the agent (present, all libraries resolved from `/opt/ros/humble`, actually starts and listens on UDP), `px4_msgs` (installed, ~235 messages, `VehicleOdometry` with `POSE_FRAME_FRD`), a publish/subscribe round trip of a `VehicleOdometry` with `BEST_EFFORT` QoS, and the DepthAI/OpenVINS packages. Run it from the host once the `entrypoint.sh` builds have finished:

```bash
sudo docker cp scripts/check_px4_bridge.sh <container_name>:/tmp/
sudo docker exec <container_name> bash /tmp/check_px4_bridge.sh
```

It exits with code 0 if every check passes. It cannot test the link with the Pixhawk; with the hardware connected, in the container:

```bash
MicroXRCEAgent udp4 -p 8888          # terminal 1
ros2 topic list | grep /fmu          # terminal 2: /fmu/out/* and /fmu/in/* must appear
ros2 topic echo --once /fmu/out/vehicle_status_v1 --qos-reliability best_effort
```

`UXRCE_DDS_DOM_ID` on PX4 (default 0) must equal the `ROS_DOMAIN_ID` of the shell, otherwise the `/fmu/*` topics are not visible. See [CLAUDE.md](CLAUDE.md).

Topic names: messages that are *versioned* in the PX4 fork get a `_v<N>` suffix, e.g. `/fmu/out/vehicle_status_v1` and `/fmu/out/vehicle_local_position_v1` (both `MESSAGE_VERSION = 1`); `VehicleOdometry` is version 0, so `/fmu/in/vehicle_visual_odometry` has no suffix. If a topic seems missing, check `ros2 topic list | grep /fmu` rather than assuming the name from the YAML.

If `ros2 topic list | grep /fmu` is empty while `uxrce_dds_client status` on PX4 says *connected*, the domains differ. Find the right one with:

```bash
for d in 0 42; do echo "domain $d: $(ROS_DOMAIN_ID=$d ros2 topic list --no-daemon | grep -c /fmu) topics"; done
```

## TagSLAM Workspace (ground truth)

TagSLAM produces the ground-truth trajectory that `ov_eval` compares OpenVINS against (see `colcon_ws/src/open_vins/ov_data/sc_fucina02/readme.md`). It reads the **same rosbag2** that OpenVINS replays: no ROS 1 conversion and no copy between containers.

- Submodule `tagslam-ws/src/tagslam` → https://github.com/berndpfrommer/tagslam, branch `ros2`. Its dependencies (GTSAM 4.2, `flex_sync`, `apriltag_detector`, `apriltag_msgs`) are `apt` packages of ROS Jazzy, so TagSLAM is the only extra package built from source.
- **A separate Jazzy container, not the Humble one.** The ROS 2 port of TagSLAM relies on rosbag2 features that Humble does not have (parametrised `Player`, `Player::get_publishers()`); its README and CI target Jazzy/Rolling, so it does not compile on Humble. A bag recorded in Humble is read as it is by Jazzy (same on-disk format, same message types), so the two containers only share mounted folders. Moving the whole repo to Jazzy would remove the second container, but it means re-validating DepthAI, OpenVINS and the uXRCE-DDS agent (v2.4.3 for Jazzy) on the hardware.
- `tagslam-ws/entrypoint.sh` builds TagSLAM with `colcon` (`RelWithDebInfo`, `-j2`; the first build takes a while) and sources `/root/tagslam-ws/install/setup.bash`. `build/` and `install/` stay in the host's `tagslam-ws/`, so later starts only rebuild what changed.
- `./dockerRun_tagslam.sh` builds the image on first use and opens a throwaway shell (`--rm`). It mounts `colcon_ws/src/open_vins` at the **same path** as `dockerRun.sh`, so the paths in the Makefile are valid in both containers. No `--net=host` and no `--privileged`: it is offline processing. A second terminal: `sudo docker exec -it tagslam bash`.

Workflow, in the Jazzy container:

```bash
make tagslam-detect   # tag detection on the raw images (slow, once per bag)
make tagslam-run      # TagSLAM on the detected tags (repeat while tuning the config)
make tagslam-gt       # trajectory -> OpenVINS_eval/truths/<TEST>.txt
```

then `error_singlerun` / `error_dataset` in the Humble container, as in the evaluation readme. `TEST`, `TAGSLAM_BAG`, `TAGSLAM_DIR` and `TAGSLAM_BODY` can be overridden on the command line (defaults: `test_3`, the bag in `ROSBAG_PLAY_DIR`, `rosbags/<TEST>/tagslam_v1`, `rig`).

The TagSLAM configuration (`cameras.yaml`, `tagslam.yaml`, `camera_poses.yaml`) goes in `rosbags/<TEST>/tagslam_v1`, next to the OpenVINS one. The ROS 1 files in `kalibr-TagSLAM/data/<test>` can be reused after changing `cameras.yaml`: `rostopic` → `image_topic`, pointing at the **raw** images in the bag (`/oak/left/image_rect`, not the ROS 1 `annotated_images`), and `tagtopic` → `tag_topic`; `tag_detector: mit` keeps the MIT detector of the ROS 1 launch file (the default is `umich`). **Detector settings differ**: `sync_and_detect` in ROS 2 runs the detector with its plugin defaults (tag family 36h11, black border 1, no decimation) and has no parameter for them, whereas the ROS 1 launch file used `black_border_width` 2. Check the detections on a bag whose ground truth you already have before trusting a new one. `kalibr-TagSLAM` stays the place for Kalibr (ROS 1) calibration.

## PX4 VIO Bridge

`colcon_ws/src/px4_vio_bridge` is a Python ROS 2 node that subscribes to OpenVINS's `odomimu` (`nav_msgs/Odometry`) and republishes it as PX4's `VehicleOdometry` on `/fmu/in/vehicle_visual_odometry`, converting frames (OpenVINS's `global`/IMU frames → PX4's FRD frames) and QoS (→ `BEST_EFFORT`) along the way. Built by `entrypoint.sh` after OpenVINS, launched with `make vio-bridge` or `ros2 launch px4_vio_bridge vio_bridge.launch.py`.

See [colcon_ws/src/px4_vio_bridge/README.md](colcon_ws/src/px4_vio_bridge/README.md) for the frame-conversion details and the full parameter reference (`colcon_ws/src/px4_vio_bridge/config/vio_bridge.yaml`), in particular `imu_to_body_rotation_deg`, which must match how the OAK-D Pro is physically mounted on your airframe.

***

## Camera Stream Viewer

`colcon_ws/src/oak_stream_server` is a Python ROS 2 node that republishes `/oak/left/image_rect` as an MJPEG stream over plain HTTP (Flask), for viewing from a browser on the same network — no ROS client needed. The container already runs with `--net=host`, so it is directly reachable on any IP the Raspberry Pi has (Wi-Fi included), no port mapping required. Assumes a trusted local network: no authentication. Launched with `make oak-stream` or `ros2 launch oak_stream_server oak_stream.launch.py`.

See [colcon_ws/src/oak_stream_server/README.md](colcon_ws/src/oak_stream_server/README.md) for the parameter reference (`colcon_ws/src/oak_stream_server/config/oak_stream.yaml`), including the `fps_limit`/`jpeg_quality` trade-off against OpenVINS's CPU budget on the Raspberry Pi 5.

## Makefile Targets

Use the Makefile inside the container after sourcing the ROS environment.

- `make depthai` — launch `depthai_ros_driver_v3` with rectified stereo streams
- `make depthai-rectified` — launch only rectified infrared streams
- `make openvins` — launch the OpenVINS example subscriber
- `make vio-bridge` — launch the OpenVINS → PX4 `VehicleOdometry` bridge
- `make oak-stream` — launch the `/oak/left/image_rect` → MJPEG HTTP stream server
- `make tagslam-detect`, `make tagslam-run`, `make tagslam-gt` — TagSLAM ground truth; **only in the Jazzy container** (`./dockerRun_tagslam.sh`, see above)

***

## Build

```bash
docker build -t <image_name> .
```

The build installs the required ROS and DepthAI components, `python3-flask` and compiles the Micro-XRCE-DDS-Agent. The workspaces (DepthAI, `px4_msgs`, OpenVINS, `px4_vio_bridge`, `oak_stream_server`) are built by `entrypoint.sh` when the container starts.

***

## Run

```bash
chmod +x ./dockerRun.sh
./dockerRun.sh <container_name> <image_name>
```

Inside the container, use the Makefile targets to launch DepthAI and OpenVINS, and `MicroXRCEAgent` to start the PX4 bridge.

`dockerRun.sh` mounts `depthai-ws`, `px4-ws`, `colcon_ws/src/open_vins`, `colcon_ws/src/px4_vio_bridge` and `colcon_ws/src/oak_stream_server` from the host. A container created before one of these mounts was added does not have it: recreate it with `dockerRun.sh`.

The TagSLAM container is started separately with `./dockerRun_tagslam.sh` (it builds its own image, `tagslam-jazzy`, from `tagslam-ws/Dockerfile` the first time), see [TagSLAM Workspace](#tagslam-workspace-ground-truth).

## Prerequisites

- Docker installed on the host
- Linux host with X11 if GUI mode is required
- `xauth` installed on the host
- git ≥ 2.25 on the host (needed for sparse checkout)
- initialise the submodules on the host, in two steps:

  ```bash
  git submodule update --init          # depthai, open_vins and tagslam; skips PX4 (update = none)
  ./scripts/init_px4_submodule.sh      # PX4 fork: shallow + partial + sparse
  ```

  Do not use `--recursive`: it would also fetch the ~29 nested submodules of the PX4 fork (not needed).
- access to the private PX4 fork from the host (git credentials for `FedericoDD/PX4-Autopilot`)
